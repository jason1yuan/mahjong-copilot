# 认牌方案评测报告（#24）

日期：2026-10-21。原始结果、逐张明细、环境与版本、实验过程记录都在 [ml/experiments/2026-10-21-tile-recognition/](../ml/experiments/2026-10-21-tile-recognition/)，其中 [NOTES.md](../ml/experiments/2026-10-21-tile-recognition/NOTES.md) 按时间记录了每一步，包括失败的尝试。

## 结论

1. **开源小型 VLM 不适合认牌。** 评测了 4 个在 Mac 上离线运行的模型（Qwen3-VL-2B / 4B、SmolVLM2-2.2B、InternVL3-2B），最好的 Qwen3-VL-4B 在 1297 张牌上只有 38.2%，每张约 0.5 秒；把图像 token 加到 1024 也只有 43.5%，每张却要 3.7 秒。
2. **在线的 OpenAI Decisions API 也不够准。** 直接问只有 30–39%；附上一张 34 种牌的对照表后升到 80.4%，但仍然不如下面的专用模型，而且要联网，和离线要求冲突。
3. **推荐用现成的专用认牌模型 pjura/mahjong_soul_vision，加一条按颜色判断赤五的规则。** 不需要我们训练任何模型。在 10 张来源独立的真实截图（132 张手牌）上 **全部正确**；在 2640 张多源模拟手牌上 97.1%，窗口宽度 ≥ 960 像素时 100%。
4. **使用条件：游戏窗口宽度至少约 960 像素。** 更小的窗口下，索子之间、5 和 9 之间开始混淆。
5. **还不能宣称达到 99.5% 的目标。** 132 张全对时，95% 置信区间的下限是 97.2%；要证明 ≥ 99.5%，需要约 600 张来源独立的真实牌全部认对。

## 结果

### 本地 VLM（D）

| 模型 | 准确率（1297 张） | 不计赤五 | 自由回答（170 张） | 单张耗时 | 峰值内存 | 文件大小 |
|---|---|---|---|---|---|---|
| Qwen3-VL-2B | 18.0% | 18.4% | 1.2% | 239 ms | 6.7 GB | 1.55 GB |
| Qwen3-VL-4B | 38.2% | 43.4% | 21.2% | 530 ms | 7.2 GB | 2.95 GB |
| SmolVLM2-2.2B | 3.4% | 4.5% | 0% | 699 ms | 5.9 GB | 1.71 GB |
| InternVL3-2B | 6.2% | 6.2% | 0% | 482 ms | 7.1 GB | 1.45 GB |

- 默认用语法约束答案（只能回答"数字 + 花色"或字牌名称）。不加约束时，模型大多在复述提示词。
- 按 llama.cpp 的提示，给 Qwen 模型加到至少 1024 个图像 token：2B 在 170 张上升到 22.9%、每张 2.3 秒，4B 升到 43.5%、每张 3.7 秒。
- 提示词里只要举了具体答案作例子，小模型就会照抄：一次运行里 1297 张有 1059 张都答成例子里的"9 characters"。最终的提示词不含任何具体答案。
- Qwen3-VL-4B 明显偏向回答赤五：1297 张里有 741 次答成赤五，而真正的赤五只有 62 张；6 筒、9 索、7 索等常被答成赤五。提示词最后一行专门讲了赤五，可能诱导了这种偏向；去掉这一行的对比还没做。
- 准确率按改正后的赤五标签计算。最初的评分沿用数据集的 34 类标签，把赤五当普通的五，审查时发现后用 [rescore.py](../ml/vlm_eval/rescore.py) 按保存的逐张答案重算，没有重跑模型。

### OpenAI Decisions API

| 数据 | 做法 | 准确率 | 不计赤五 | 置信度 ≥ 0.7 时 | 每次请求 token | 费用 |
|---|---|---|---|---|---|---|
| D，170 张 | 原始 | 39.4% | 43.5% | 21/21，覆盖 12% | 792 | $0.013 |
| S1，520 张 | 原始 | 30.4% | 33.1% | 25/25，覆盖 5% | 789 | $0.041 |
| S1，520 张 | 放大到长边 512 像素 | 22.1% | 30.6% | — | 940 | $0.049 |
| S1，520 张 | 放大 + 请求高清晰度 | 22.1% | 30.6% | — | 940 | $0.049 |
| S1，520 张 | 放大 + 附 34 种牌的对照表 | **80.4%** | **85.4%** | **244/244，覆盖 47%** | 1559 | $0.081 |
| S1，520 张 | 放大 + 拆成花色、数字、字牌、赤五四道题 | 45.4% | 48.5% | 77/81，覆盖 16% | 899 | $0.047 |

- 单张耗时中位数 156–287 ms（含网络往返）。
- 放大只多了约 150 个 token，"高清晰度"参数的结果和只放大完全相同，看来被忽略了。
- 高置信度的答案几乎全对，可以用来"拿不准就不认"：附对照表时置信度 ≥ 0.7 的 244 张全对，但只覆盖不到一半的牌。
- 置信度本身偏保守，不能直接当成答对的概率。每种做法报出的平均置信度都低于实际准确率，例如附对照表时平均置信度 0.61、实际准确率 0.80。按 10 个等宽区间算的校准误差（ECE）：原始做法 0.08（S1）和 0.13（D），附对照表 0.20。
- 典型错误：8 索认成發，6 筒认成 5 筒，3 索认成 2 索，8 万、9 万认成 1 万。

### 推荐方案：pjura/mahjong_soul_vision + 赤五颜色规则

| 数据 | 只用分类器 | 分类器 + 赤五规则 | 95% 置信区间 |
|---|---|---|---|
| **R，真实截图，132 张** | 97.0%（不计赤五 100%） | **100%（132/132）** | [97.2%, 100%] |
| SM，多源模拟，2640 张 | 94.1%（不计赤五 97.1%） | 97.1% | [96.4%, 97.7%]，样本相关，区间偏乐观 |
| S1，单源模拟，520 张 | 85.4%（不计赤五 91.3%） | 91.3% | — |
| D 测试部分，去重后 181 张 | 不计赤五 100% | —（阈值在 D 上定，不算验证） | [97.9%, 100%]（不计赤五） |

窗口宽度的影响（SM，不计赤五）：

| 窗口宽度 | 480 | 600 | 800 | 960 | 1280 | 1600 | 1920 |
|---|---|---|---|---|---|---|---|
| 准确率 | 88.8% | 90.2% | 96.6% | 100% | 100% | 100% | 100% |

- **赤五规则**：分类器只认 34 种牌，不区分赤五。普通的五都有非红色笔画（5 万的黑色"伍"、5 筒的黑色圈、5 索的绿竹子），赤五只有红色，所以"非红色笔画占比"低于 0.25 就判为赤五（[red_five.py](../ml/vlm_eval/red_five.py)）。阈值只用数据集 D 里的 145 张五来定（赤五 ≤ 0.20，普通五 ≥ 0.30，完全分开），再在没参与定阈值的 R 和 SM 上验证：R 中赤五 4/4、普通五 8/8；SM 中赤五 80/80。唯一一次误判出现在 480 宽窗口加模糊、牌图只有 23×36 像素时。
- **数据集的标签问题**：D 没有赤五类别，它的"五"文件夹里混着 62 张赤五。逐张人工判断的结果在 `annotations/dataset_red_fives.json`。
- **速度**：单张 38–76 ms（CPU，PyTorch）；整手 14 张一次识别，CPU 约 273 ms，Mac GPU 约 127 ms。模型文件 343 MB，运行内存约 1 GB。

## 推荐的认牌流程

1. 用适配包和画面配准定位手牌，按牌位切图（`find_hand.py` 是标注用的原型）。
2. 变化检测：只处理变了的牌位。
3. 先查运行时模板缓存，命中就直接采用（几毫秒）。
4. 没命中：交给 pjura/mahjong_soul_vision，认出是五时再用颜色规则判断赤五，结果存进缓存。
5. 分类置信度低或牌图太小（宽度不到约 30 像素）时，在界面上标"?"，不要硬猜。
6. 提示用户把游戏窗口宽度调到至少约 960 像素。

部署前还要做：

- 把它的 PyTorch `.bin` 权重转成 ONNX，在 Rust 里用 ONNX Runtime 运行，并做输出对照测试。（#4 已完成，2989 张牌的结果和 PyTorch 完全一致）
- 试 fp16 / int8 量化以缩小体积，量化后要在 R 上重新验证准确率。（#4 试了 int8：R 上同样全对，但数据集测试部分多错一张，先不用）
- 定下模型文件的下载来源。这里原先建议由 app 直接从原作者的仓库下载；但原仓库只有 PyTorch 权重，app 读不了。#4 最后定为把转换后的 ONNX 放在我们自己的 Hugging Face 仓库，见设计文档。

VLM 不用于认牌；MLX 运行方式的对比因此没有做。数字和按钮的识别（#9）另行评估。

## 还需要进一步验证

- 扩充真实截图到约 600 张牌以上，才能在统计上确认 ≥ 99.5%；优先补小窗口、Steam 客户端、其他牌面皮肤，以及赤五筒和 7 筒（目前 R 里没有）。
- 牌河和副露：有透视、颠倒和横放，本次只评测了手牌。计划用牌谱回放录屏自动生成带标准答案的画面（#18）。
- 数字、按钮和分数的识别（#9）。
- 极小牌图上的赤五误判：按牌图大小调整判断，或直接标为不确定。

## 复现

在仓库根目录：

```bash
python3 -m venv ml/.venv && ml/.venv/bin/pip install -r ml/requirements.txt
```

```bash
ml/vlm_eval/run_all.sh
```

```bash
ml/.venv/bin/python -I ml/vlm_eval/eval_vit.py --simulated recordings/source --red-rule
```

```bash
ml/.venv/bin/python -I ml/vlm_eval/report.py
```

- 本地 VLM 需要 llama.cpp（`brew install llama.cpp`）。数据集会下载到 `ml/data/`，模型下载到 `ml/models/`，都不进 git。
- 真实截图需要自己准备；标注在 `ml/experiments/2026-10-21-tile-recognition/annotations/`，图片的哈希在 `manifest.json`。
- 新的评测直接用改正后的赤五标签（`config.toml` 里的 `red_fives`）。改了标签或评分方法后，用 `ml/vlm_eval/rescore.py` 按保存的逐张答案重算全部结果，不用重跑模型。
- 模拟截图用 `ml/vlm_eval/simulate.py` 按标注重新生成。随机种子固定，但如果原图不是同一批文件，生成结果也会不同。
- Decisions API 需要你自己的 API key，见 `ml/vlm_eval/eval_decisions.py` 的说明。
